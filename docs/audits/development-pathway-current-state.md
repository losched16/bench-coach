# Development pathways — current state

Phase 2E.1. Written before any schema is designed, against `e498235` and
production as of 2026-09-17.

The brief's instruction is "do not duplicate an existing model". This document
exists to establish what the existing models actually are, because two of them
are named differently in the brief than they are in the code, and one of them
has never been used.

---

## 1. What exists

| Thing | Where | Shape |
|---|---|---|
| `development_plan` | **JSONB column on `prescriptions`** (migration 023) | `{ markdown, weeks, generated_at, drill_ids, sessions[] }` |
| session completion | **`plan_session_log` table** (migration 035) | one row per session ticked off |
| `plan_steps` | JSONB column on `prescriptions` (migration 036) | `[{ n, title, why, drillIds[], moveOnWhen[] }]` |
| `current_step` | INT column on `prescriptions` (036) | 1-based, advanced by a human |
| `step_advanced_at` | TIMESTAMPTZ on `prescriptions` (036) | when they last moved up |
| step derivation | `lib/progression.ts` | 3 stages from `progression_level` |
| generation | `app/api/development-plan/route.ts` | one Opus call, 398 lines |
| ticking off | `app/api/plan-sessions/route.ts` | GET/POST/DELETE on `plan_session_log` |

**Two naming corrections to the brief's baseline.** There is no
`development_plan` *table* — it is a column. There is no `plan_sessions` table —
it is `plan_session_log`, and it records completions rather than plan content.

---

## 2. The finding that matters most

```
prescriptions                 0 rows
prescriptions with a plan     0
prescriptions with steps      0
plan_session_log              0 rows
```

**Nobody has ever generated a development plan in production.** The schema is
applied, the routes are live, the model prompt is written — and the entire
player-plan layer has zero rows behind it.

Two consequences, and they point in opposite directions:

- **Reuse is cheap.** There is no data to migrate, no stored shape to stay
  compatible with, and no coach whose plan would change under them. 2E.8's
  "reuse `development_plan` / `plan_sessions` as the instance layer" carries
  none of the usual risk.
- **The model is unvalidated.** "It already works, build on it" is not a claim
  the data supports. Nothing about the three-week, one-priority, prose-first
  shape has been tested against a real coach.

For contrast, the surfaces that *are* used: 15 practice plans, 4 player
reports, 8 teams, 61 players, 11 coaches. Practice Plan is the live surface.
The player development plan is not.

## 3. What each existing model actually is

### `development_plan` — a written answer to one priority

Generated by Opus against ONE prescription, for a parent with twenty minutes in
a driveway. Three weeks, two or three sessions a week, prose plus a structured
`sessions` tail. Stored on the priority and **explicitly dies when the priority
closes** ("a plan that outlives its reason is a plan nobody trusts").

It is player-specific, disposable, and model-authored. It is not reusable, not
curated, and not shared between players.

### `plan_steps` + `lib/progression.ts` — a difficulty ladder, not a curriculum

This is the closest existing thing to sequence intelligence, and the distinction
is the whole reason Phase 2E exists.

```ts
const STAGES = [
  { level: 1, title: 'Get the feel'      },  // slow, static, no ball
  { level: 2, title: 'Make it stick'     },  // with the ball, controlled
  { level: 3, title: 'Take it to the game' },  // game speed, reacting
]
```

Three stages, derived from `drill_resources.progression_level`, **identical for
every skill in baseball**. It knows that a tee drill is easier than front toss.
It does not and cannot know that an athletic stance comes before a grip comes
before a load comes before a stride.

It is a *how hard* axis. A pathway is a *what next* axis. They are orthogonal,
and a stage in a pathway will contain drills from several difficulty levels.

**Evidence that difficulty is not sequence**, from the library itself:

- `Turn and Take It` is `progression_level 1` and is about not being afraid of
  being hit. It is not step one of building a swing; it is a different concern
  that runs alongside.
- `Freeze at Extension Drill` is level 3 and teaches a finish position — which
  belongs early in bat-path work, not two gates in.
- `Front Toss` has **no `progression_level` at all** and is the single most
  important bridge between tee work and live pitching.
- `Stance & Athletic Position Drill` is level 1 and genuinely is stage one —
  the levels are sometimes right, which is what makes trusting them dangerous.

`progression_level` is populated on **92 of 154** schedulable drills. Sorting a
pathway by it would put 62 drills in an arbitrary place.

### `prescriptions` → drills — problem-driven, not sequence-driven

`/api/prescribe` diagnoses a coach's complaint into `problem_taxonomy` slugs,
maps through `drill_problem_map`, and returns drills for THAT problem. It
answers "what fixes this?" and has no opinion on "what comes next?".

Note `/api/prescribe/route.ts:238` passes `{ practiceUnits: false }` — the
prescribe pool is narrower than the general schedulable pool. Any pathway
recommendation has to be honest about which pool it is drawing from.

### Practice Plan — the live surface, and the right place to land

`/api/practice-plan` takes `teamId`, `duration`, `focus[]`, `constraints`,
runs `retrieveDrills`, and writes a plan with Opus. `focus` is one of seven
`FocusArea` values (`lib/focusAreas.ts`) — coarse, unordered coaching areas.

A pathway is a finer, **ordered** layer beneath a focus area:

```
focus area 'hitting'  →  pathway 'build-the-swing'  →  stage 4 'load to launch'  →  drills
```

That is the gap. Nothing in the product currently occupies it.

## 4. Fields already curated that a pathway can build on

These matter because 2E must not invent what already exists.

| Field | Coverage (154 schedulable) | Used by |
|---|---|---|
| `practice_roles` | **153** | Drill Finder chips, instruction gate. **Nothing sequences with it.** |
| `success_markers` | **154** | Drill Finder "Watch for", `progression.ts` gates |
| `regression_notes` | **154** | Drill Finder "Make it easier" |
| `progression_notes` | **154** | Drill Finder "Make it harder" |
| `drill_problem_map` | 153 drills, 393 rows | prescribe, Drill Finder search |
| `activity_family_id` | 33, across 18 families | `practiceScheduler` redundancy, Finder variations |
| `progression_level` | 92 | `lib/progression.ts` |

**`practice_roles` is the important one.** Its vocabulary is already:

```
warmup · teach · isolate · repetition · progress · decision ·
game_application · team_execution · competition · finish
```

2E.7 asks for `prepare → teach → isolate → repeat → progress → decide →
compete → apply`. That is very nearly the same vocabulary, curated, populated
on 153 of 154 rows, and currently read by nothing that sequences a practice.
Sequence intelligence should be built on this field rather than on a new one.

## 5. What is missing

Nothing in the product can answer any of 2E.8's six questions:

| Question | Closest existing answer | Why it fails |
|---|---|---|
| What stage are we on? | `prescriptions.current_step` | Per-priority, per-player, and 0 rows exist. Nothing at team level. |
| What should we teach next? | — | `progression.ts` says "harder", not "next". |
| Which drills reinforce it? | `drill_problem_map` | Keyed on a *problem*, not on a teaching stage. |
| How do we assess mastery? | `success_markers` | Per-drill. No stage-level mastery signal. |
| When should we advance? | `moveOnWhen` | Union of per-drill markers, not a stage gate. |
| What do we regress to? | `regression_notes` | Per-drill, textual. Not a pointer to an earlier stage. |

Specifically absent:

1. **A reusable, curated teaching sequence.** Everything ordered today is either
   derived from difficulty or authored per-player by a model.
2. **A stage as a first-class object** with an objective, a prerequisite, a
   mastery signal and failure modes.
3. **A many-to-many stage↔drill link with a role.** `drill_problem_map` is the
   only existing drill join and it carries a problem, not a teaching function.
4. **Anything at team level.** All progression state hangs off `prescriptions`,
   which is per-player.

## 6. What must not be duplicated

- **Do not build a second difficulty model.** `lib/progression.ts` owns that.
  Pathway stages are a teaching order; difficulty stays where it is and should
  be used for *ranking within a stage*, never for choosing the stage.
- **Do not build a second problem→drill map.** `drill_problem_map` is curated
  and 393 rows deep. A stage should *reference* the problems it addresses.
- **Do not build a second schedulable filter.** `lib/drills.ts` owns
  visible/schedulable. A pathway service must narrow it, never restate it.
- **Do not build a second media layer.** `lib/drillMedia.ts` owns that, and
  Phase 2D established that video is optional.
- **Do not replace `development_plan`.** If a pathway ever needs a per-player
  instance, that column and `plan_session_log` are the place — they are empty,
  so the fit can be decided on merit rather than on migration cost.

---

## 7. Conclusion for 2E.2

A canonical pathway layer is genuinely new. It sits:

- **above** `drill_resources` — a stage names an objective and lists drills that
  serve it, with a role each;
- **below** `practice_plans` and `prescriptions` — it recommends, it does not
  schedule;
- **beside** `problem_taxonomy` — a problem is "what is broken", a stage is
  "what we are teaching next", and a stage may address several problems;
- **orthogonal to** `progression_level` — which ranks options inside a stage.

It should be curated and versioned rather than derived, because the judgement in
it is coaching judgement. That is the same reasoning `lib/progression.ts` gives
for deriving rather than generating — and it lands the opposite way here,
because an ordering of *teaching content* cannot be computed from any column the
library has.
